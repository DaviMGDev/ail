REASONING CHAINS:
- Spec-as-implementation insight (from "no tooling") is now softened: with no runtime, the binding constraint is not interpreter-readability but internal consistency — a controlled language whose own definition is ambiguous is a bad design even on paper.
- Elegance hypothesis for the fork: minimal extension = sequence + branch + loop + procedure call, expressed in ACE-flavored syntax obeying the inherited golden rules (determiners, 3rd-person present, punctuation). The design criterion: how few new function words/constructs cover the imperative space while reading like ACE.
- Branching is likely the keystone primitive: it forces decisions about state, failure, and scope that sequences, loops, and procedures all inherit.

KEY INSIGHTS:
- ACE's declarative/command split (facts/rules vs. "John, go to your own bank!") already prefigures the knowledge/control split ACL needs — the fork is a continuation, not a rupture.
- For a design exercise, the test of the language is expressiveness-by-example: can ACL say "check the card; if valid insert it, otherwise reject it" unambiguously and readably?
